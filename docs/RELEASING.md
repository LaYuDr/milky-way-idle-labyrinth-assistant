# 发布流程

## 当前状态与首次配置

首次发布准备版本为 0.12.6。`release.config.json` 的 repository、downloadURL、updateURL 故意为空。
发布预演和正式发布会在缺少渠道时失败，不会猜测仓库名或误用公会助手条目。

首次发布前，在获得创建和发布授权后：

1. 创建独立 GitHub 仓库，设置 origin 和 main。提交并推送工程基线，使本地 HEAD 与 origin/main 一致。
2. 首次 Greasy Fork 条目需要在网站创建，不能靠 Git 推送自动创建。以明确授权的首个脚本上传创建条目，取得新条目 ID。
3. 将独立仓库 HTTPS 地址（不带 `.git`）及同一 Greasy Fork 条目的 `.user.js`、`.meta.js` 地址填入配置；启用该条目从 GitHub 当前安装入口同步的设置。
4. 首次上传如果已使用 0.12.6，正式同步版本必须提升到 0.12.7，避免已安装用户漏更。首次上传的历史产物也应保留并登记；不要声称此前已有自动归档。
5. 确认该版本的功能、权限和实际游戏验证结果，再执行下面流程。

首次网站建条目与配置同步仍需平台操作。仓库脚本不保存平台凭据、不替用户首次建条目。

## 日常发布

先明确维护 `package.json`、`package-lock.json` 的两个根版本字段，以及 `CHANGELOG.md` 中的 `## X.Y.Z` 条目。新版本必须高于历史全部版本。
版本不自动递增，变更说明不自动代写，便于清楚复核发布内容。

```bash
npm run release:dry-run
# 已授权发布后
npm run release
```

也可双击 `发布当前版本.command`。该命令会提交并推送，不能拿它代替本地构建。

预演只读、不联网，核对配置、独立仓库、main 分支、空暂存区、origin 拉取/推送地址、缓存远端提交、版本、变更记录和文件白名单，列出发布计划。它不代表远端实时状态或测试通过。

正式发布重新 fetch 后检查同步状态，再运行完整门禁、创建历史归档、验证 SHA-256、显式暂存、提交和推送。推送后核对 GitHub 提交及 Greasy Fork 完整脚本内容。未配置渠道、暂存区非空、未推送提交、落后远端、未允许文件或历史修改都会阻止发布。

普通构建只写 dist。正式归档位于 `releases/v主版本.次版本/迷宫助手-v完整版本.user.js`，清单记录版本、路径、字节数和 SHA-256。旧归档不可覆盖。

## 中断与回滚

- 测试失败：修复后重新预演；不会提交或推送。
- 已生成归档但尚未提交：检查本次文件和暂存区，不可覆盖旧历史。确认本次未公开后，人工整理本次未完成产物，再重新准备。
- 已提交但推送失败：保留提交和归档，检查原因、提交范围及远端状态；获得既有发布范围内授权后推送该提交。发布脚本会拒绝存在未推送提交，不会自动重做版本。
- GitHub 已推送但 Greasy Fork 未同步：稍后核对条目同步设置及公开脚本，不能重复运行发布来伪造成功。
- 已发布版本有缺陷：修复或恢复源码，发布更高补丁版本；不改写历史，不强制推送回滚。

不并行编辑正在发布的文件。脚本无法保证多人同时写工作区时的发布一致性；发布应在独占或隔离的 checkout 中进行。
